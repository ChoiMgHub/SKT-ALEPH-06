# 플랜드씨 다이어리 — 6장 과제

계획(Plan) → 실제 실행(Do) → 근거를 보며 돌아보기(See)를 이어 쓰는 공개 다이어리입니다. 공개 앱에는 이 과제를 수행하며 등록한 **「6장 과제 완성하기」 계획 1개, 그 할 일 5개, 실행 기록 3개**가 있습니다. 여기에 기존 회고를 전달한 **「6장 과제 배포 후 제출 전 최종 확인」 계획과 검수 할 일·실행 기록을 각각 1개씩** 추가했습니다. AI 지원을 받은 작업임을 아래에 공개합니다. 실행 기록 합계는 등록된 기록의 시간이며 전체 개발 시간을 뜻하지 않습니다.

## 짧은 확인 방법 — 4줄

1. 어디로 가나요: 위 결과물 주소를 새 브라우저에서 열면 로그인 없이 계획·할 일·실제·돌아보기 화면이 나옵니다.
2. 세 단계 안에 무엇을 하나요: ① 계획과 연결된 할 일을 저장 → ② 완료 처리와 실제 시작·종료 시각을 각각 기록 → ③ 돌아볼 계획을 골라 집계 숫자와 근거 링크를 누릅니다.
3. 무엇이 보이면 통과인가요: 수정 전 계획이 남고, 완료 이력·집계가 중복되지 않으며, 실제−예상 차이와 원본 기록이 보입니다. 회고 한 줄을 다음 계획으로 넘겨 저장하고 JSON 내보내기·새로고침 후에도 같은 자료가 남아야 합니다.
4. 안 될 때는 무엇이 보이나요: 입력 오류·저장 실패·서버 자료 읽기 실패는 화면 상단에 오류 메시지로 표시됩니다. 필수 입력과 네트워크를 확인하고 다시 시도하세요.

## 구현한 기능

- 계획의 기간·우선순위·성공 기준·예상 시간 저장, 같은 ID를 유지하며 수정 직전 값 별도 보존
- 할 일 생성·수정·완료·되돌리기·삭제, 마감·우선순위·분류(태그)·예상 시간, 검색·필터·정렬과 동률 규칙 표시
- 완료 상태 갱신과 완료 이력 저장을 한 트랜잭션으로 처리, DB 기본키로 할 일당 최초 완료 한 건 보존
- 완료 이력과 실행 시간 기록 구분: 완료 버튼이 시작·종료 시각이나 실제 작업 시간을 임의로 만들지 않음
- 실행 기록의 시작·종료·실제 시간·달랐던 이유를 할 일에 연결, 요청 ID의 UNIQUE 제약으로 재전송·동시 요청 중복 방지
- 계획별로 삭제하지 않은 할 일의 계획 수·완료·지연·막힘·예상·실제·차이 집계, 숫자 → 근거 목록 → 원본 기록 이동
- 돌아보기 문장을 다음 계획 작성 양식으로 전달하고, 저장 시 원본 계획·새 계획·전달 당시 문장을 함께 보존
- 계획·수정 이력·삭제된 항목까지 포함한 할 일·실행·완료 이력·돌아보기·다음 계획 연결을 JSON 파일 하나로 내보내기

## 집계·시간 규칙

돌아보기의 **계획 수는 선택한 계획에 속한 삭제하지 않은 할 일 수**입니다. 계획 묶음의 개수와 구분합니다. 완료는 현재 `done`, 지연은 미완료이면서 마감이 서버 판정 시각보다 앞선 항목, 막힘은 이유가 적힌 항목 수입니다. 모든 집계가 같은 서버 판정 시각을 사용합니다.

예상은 대상 할 일 예상 시간의 합계, 실제는 그 할 일 실행 기록의 합계, 차이는 **실제−예상**입니다. 계획 묶음의 예상값을 중복해서 더하지 않습니다. 빈 자료는 0, 예상보다 실제가 짧으면 음수입니다. 기존 계획의 등록값으로 계산하면 예상 95분·실제 3분·차이 −92분입니다.

계획 기간은 시간대 없는 달력 날짜입니다. 마감과 실행 시각은 기기 시간대로 입력·표시하고 서버는 UTC ISO 문자열로 저장합니다. 모든 시간 수치는 정수 분이며 실제 시간은 시작·종료 차이를 가장 가까운 분으로 반올림합니다. 기록하지 않은 시간은 집계하지 않습니다.

완료를 진행 중으로 되돌리면 현재 완료 집계는 줄지만 최초 완료 이력은 보존합니다. 다시 완료해도 이력을 추가하지 않습니다. 업그레이드 전에 이미 완료된 항목은 기존 마지막 수정 시각에서 이력을 복원하고 `existing_status`로 출처를 구분합니다.

## AI와 내 판단 — 3줄

1. AI에 맡긴 일: 요구사항 분석, 화면·서버·데이터베이스 설계와 구현, 테스트, 기준별 검수 및 보완, 배포 준비와 공개 앱 최종 확인.
2. 내가 직접 판단하고 수행한 일: 기술 작업에 AI 도움을 받기로 하고 여섯 장의 과제 기준 전체 보완을 요청했습니다. 이후 내 Windows PC에서 Node.js 설치, 테스트 실행, Cloudflare 로그인 승인, 원격 DB 적용과 앱 배포를 직접 실행하고 출력을 확인했습니다.
3. AI 제안을 따르지 않은 일: 현재 대화에서 확인된 별도 사례는 없습니다. 이번에는 안내 기준에 맞춘 전체 보완을 AI에 맡기기로 했으며, 실제로 하지 않은 판단·검증을 내가 했다고 적지 않습니다.

## 공개·보안 안내

현재 로그인 기능이 없으므로 **링크를 아는 사람은 내용을 읽고 수정할 수 있습니다. 남이 봐도 괜찮은 내용만 넣으세요.** 다른 사람의 이름·연락처나 민감한 정보를 적지 마세요. 계정별 비공개 보관은 이번 과제 범위에 없습니다.

사용자 입력은 `textContent`로 표시하고 SQL은 매개변수 바인딩을 사용합니다. 정적 자산의 보안 헤더는 `public/_headers`, 단일 파일 배포의 헤더는 빌드 스크립트에서 설정합니다. 소스·브라우저용 코드·내보내기에 API 키·비밀번호·배포 토큰을 넣지 않으며 서버 저장 오류는 원문 데이터 대신 일반 메시지만 로그에 남깁니다. D1 데이터베이스 ID는 인증 토큰이 아닙니다.

## 개발·테스트·배포

Node.js **22.13 이상**을 사용합니다. `package-lock.json`을 포함하므로 `npm ci`로 같은 의존성을 설치합니다.

테스트용 Ajv는 알려진 취약점 수정 버전인 8.20.0으로 고정했습니다. 설치 스크립트는 배포 도구에 필요한 `esbuild@0.28.2`와 `workerd@1.20261019.1` 두 버전만 `allowScripts`에 명시했습니다. npm 자체의 새 주요 버전 안내나 `whatwg-encoding` 폐기 예정 안내는 설치 실패 메시지가 아닙니다. 자동으로 `npm audit fix --force`를 적용하지 않습니다.

Windows PowerShell에서는 아래 명령의 `npm`·`npx`를 각각 `npm.cmd`·`npx.cmd`로 실행할 수 있습니다. Bash용 `export PATH=...`는 PowerShell에서 사용하지 않습니다.

```bash
npm ci
npm test
npm run build
```

테스트는 메모리 SQLite에서 API와 트랜잭션을 검증하고, jsdom에서 실제 화면 코드를 실행해 입력·검색·완료·회고 연결·스크립트 모양 문자의 안전한 표시를 확인합니다. 자동 테스트 자료는 실제 개인 활동 기록이 아니며 공개 D1에 넣지 않습니다.

로컬 실행:

```bash
npm run db:local
npm run dev
```

기존 Cloudflare 계정과 D1 바인딩을 유지하며 배포합니다. **새 코드 배포 전에 DB 스키마를 먼저 적용**합니다. `schema.sql`은 기존 테이블·기록을 삭제하지 않고 새 이력·연결 테이블을 추가합니다. 원격 작업 전에는 공개 앱의 내보내기로 기존 자료를 보관합니다.

```bash
npx wrangler login
npm run db:remote
npm run deploy
```

CLI 대신 대시보드에서 배포할 경우 D1 콘솔에 `schema.sql`을 적용한 다음 `npm run build`로 만든 `dist/worker.js`를 기존 Worker의 코드로 배포합니다. `DB` 바인딩은 `aleph-diary`를 유지합니다. 상태 점검 `/api/health`의 `implementation_version`이 `pds-v2-2026-10-22`이고 화면 하단이 `v2`인지 확인합니다. **GitHub 소스 반영만으로 기존 수동 배포 앱이 갱신되는 것은 아닙니다.**
